## 1. 现状与关键结论

- 基座首页卡片来自后端 `portal/index`（`center.urls`），点击默认 `window.open` 新页签打开 `data.url`。
- 基座顶部菜单/左侧菜单/路由表全部来自后端 multiMenu 系列接口：`multiMenu/view/top`、`multiMenu/view/children`（`getAuthAndSubMenu`）、`multiMenu/view/allRoute`（`getAllRouteByPCode`）。
- 左侧菜单点击 → `loadApp` → `dispatchAppState` + `history.pushState(menu.router)` → qiankun 子应用渲染。
- **React 子应用能响应 pushState 是因为 React Router 的 history 库 monkey-patch 了 pushState；vue-router 4 没有**。因此 DS（Vue3）需要自己做 pushState→vue-router 桥接，否则基座菜单点击后 URL 变了但内容不切换。

## 2. 总体设计：dev 等效层 + 生产配置层

后端菜单（dlite-portal，远端 10.200.8.134）我们无权配置，采用与「代理注头」相同的策略：

- **dev 等效层（本期实施）**：基座前端在 service 层对 4 个接口做响应合并（shim），注入与后端配置完全同构的「海豚调度」菜单数据。联调/验收都在此层完成。
- **生产配置层（本期输出配置说明）**：平台方在 multiMenu 按同构数据配置后，删除 shim 即切换，前端零改动。网关分流与密钥注入给 nginx 示例。

shim 集中在一个新文件 `dlite-front-main/src/service/dolphinschedulerMenuShim.js`，`global.js` 仅在 4 个函数出口调用其 post-process 函数，每处一行、带注释标记，便于下线。

### 6.2 网关分流（nginx 示例，页面/API 同前缀按 Accept 分流，与 dev 代理同策略）

```nginx
server {
  listen 80;
  location /dolphinscheduler/ {
    # 浏览器页面导航（HTML）→ 基座
    if ($http_accept ~* "text/html") { proxy_pass http://dlite-front-main; }
    # API → DS 后端
    proxy_pass http://dolphinscheduler-api:12345;
    proxy_set_header Host $host;
    client_max_body_size 0;
  }
  # 可信登录端点：仅允许网关注入密钥、内网来源；禁客户端直传
  location = /dolphinscheduler/login/trusted {
    allow 10.0.0.0/8;      # 网关/内网白名单
    deny all;
    proxy_pass http://dolphinscheduler-api:12345;
    proxy_set_header X-Trusted-Client "<部署注入的密钥>";
    proxy_set_header Host $host;
  }
}
```

注意：`if` 块内 proxy_pass 不附带路径替换，保持原始 URI；生产建议同时收敛 DS 后端仅网关可达。密钥不入库不入仓，走部署环境变量。

### 7.1 实施期修正记录

1. **product/子系统编码必须是 dlite- 前缀**（最终值 `dlite-dolphinscheduler`）：两个坑的合解——① 裸编码（dolphinscheduler）会让 appInitialRequest 用未知 systemCode 调 7 个后端接口，任一失败即白屏（multipleRequest 无 catch，已加 catch 兜底）；② 基座对 dlite-* 的 systemCode 才按 `sub_system_code` 过滤菜单权限编码，这是"顶栏只显示当前应用 tab"的作用机制，其他应用均依赖此机制实现 tab 作用域。DML 中所有菜单行的 `sub_system_code` 同步为该值。
2. **顶部菜单 childrenNav 必须为 true**：主框架仅对 childrenNav/projectFlag 菜单执行 setState(loading:false)，false 时永远卡在 loading 门（无异常白屏）。已同步修正 4.1 数据。
3. **getAuthAndSubMenu 加 try/catch 兜底**：children 接口对未知 parentCode 可能报错，仅对 dolphinscheduler 的菜单请求失败做合成数据回调，其余保持原行为。
4. **全部产品抽屉（左上展开菜单）**：数据源为 `portal/products`（产品+moduleList 顶部菜单），已加 `shimProducts` 合并合成产品项（全局追加，抽屉本是全局产品列表）；抽屉内点击走 `collectMenuClick`，依赖 module 项的 `url` 字段，合成数据已补。
5. **未知/陈旧 `/dolphinscheduler/*` 路径**（旧链接直访，如实测复现：修复前的 `/resources/file-manage` 复数路径）：`allRoute` 未命中 → 基座把页面挂到默认产品（数据集成），地址与内容错配；且 qiankun 对未命中路径的挂载早于容器渲染会报 `Target container with #app-container not existed`。修复：`setTopDefaultMenu` 兜底分支命中海豚调度前缀时**整页重定向到 `/dolphinscheduler/home`**（注意必须重定向到具体入口页，重定向到 activeRule 前缀本身会造成死循环）；另在 DS router 增加 qiankun 模式 catch-all 404 提示路由（`/:pathMatch(.*)*`），消灭静默空白类问题。
6. **`auth_flag` 双语义踩坑（DML 评审疏漏，2026-11-19 角色管理实测暴露）**：初版 DML 将 9 行菜单全部写为 `auth_flag=1`（意图"免授权可见"），但该值为"不需要权限控制"——功能授权树查询 `getAllVisibleFunction` 只加载 `auth_flag=0`，导致模块在角色管理功能授权处完全不显示、无法按角色分配；而 multiMenu 的免授权查询 `queryCodeListWithoutPermission` 恰要求 `auth_flag=1`，两侧语义相反。当时只核对了"菜单可见性"一侧的查询语义，未核对"授权树"一侧。**教训：DML 字段取值必须对照该字段的全部消费查询，而非单一 happy path**。已修正 DML 为 `auth_flag=0`（超管/管理员菜单可见性不过滤该字段，实证 MultiLevelMenuServiceImpl.java:170-172），存量环境用 6.1 幂等 UPDATE 修正并清 `A_fun_user_*` 缓存。
7. **`all_parent_code` 格式踩坑（2026-11-20 本地、2026-11-25 测试环境两次复现）**：平台约定为顶级 `/`、二级 `/<父code>/`（带斜杠），`view/children` 依赖 `concat(all_parent_code, code)` 按 `/` 拆分后与菜单 code 精确匹配；初版 DML 写成空串和 `dolphinscheduler`（不带斜杠），拼接结果无法匹配任何 code——表现是左侧菜单与内容区全空（顶栏 tab 正常），且 **superadmin 也一样空**（极易误判为前端问题）。已修正 DML（6.1），存量环境用 6.1 幂等 UPDATE 自愈。
