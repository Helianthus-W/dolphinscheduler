# 基座 ↔ 海豚调度（DolphinScheduler）对接操作手册

> 配套文档：`项目一体化同步方案.md`（设计/决策），本文档是**操作与排障手册**。
> 适用版本：DolphinScheduler 3.2.2（本仓库改造版）+ dlite 基座（dlite-portal / dlite-base / dlite-front-main）。
> 最后更新：2026-11-23（本地联调环境实测整理）

---

## 1. 架构总览

```
浏览器 ──> 基座前端 dlite-front-main (:2024, qiankun 主应用)
              │
              ├── /dlite-portal、/dlite-base、/dlite-resource  ──> Tomcat (:9080, 三个 war)
              ├── /dolphinscheduler                            ──> DS 后端 (:12345)
              └── qiankun 子应用「数据开发」 entry = DS UI dev (:5180)

dlite-base ──(ds.sync 服务通道: X-Portal-User + X-Trusted-Client)──> DS 后端 (:12345)
DS 后端 ──(portal.validate-url, cookie 校验)──> dlite-portal (:9080)
数据存储：MySQL (:3306, docker 容器 micro-dataops-local) + Redis (:6379)
```

身份模型：**PORTAL 身份源**（`security.authentication.type=PORTAL`）。DS 废弃自有会话，
浏览器请求带门户 cookie（`dlite_login_token`）→ DS 调门户校验（30s 缓存，fail-closed）→
解析为本地**影子用户**（按门户用户名自动建档，密码 NULL，永不可本地登录）；
服务通道（dlite-base → DS）用 `X-Portal-User` + `X-Trusted-Client` 共享密钥断言身份。

## 2. 服务清单与启动顺序

| 服务 | 端口 | 启动方式 | 说明 |
|---|---|---|---|
| MySQL（docker） | 3306 | `docker start micro-dataops-local` | 库：dolphinscheduler / dlite_* / portal_user |
| Redis（docker） | 6379 | `docker start redis` | 门户会话（key 前缀 `global:`，TTL 30min） |
| Tomcat（portal+base+resource 三 war） | 9080 | `catalina.bat run` | war 名即 context path |
| DS 后端 | 12345 | 见 §2.1（standalone，本地联调用） | **堆别给 4g**（`jvm_args_env.sh` 的 -Xms4g 在本机起不来，见 §5.7）；测试/生产集群模式见 §2.3 |
| DS 前端（vite dev） | **5180** | 见 §2.2 | **不要用 5173/5174/5175**（MDM 项目占用区，见 §5.8） |
| 基座前端 dlite-front-main | 2024 | `npm start`（Node 16/17，见 §5.6） | qiankun 主应用 |
| 安全中心 dlite-front-security | 7081 | `npm start`（**Node 17**） | 用户/角色/授权 |
| 菜单管理 dlite-front-system | 7083 | `npm start`（**Node 17**） | multiMenu 菜单树管理 |

启动顺序：MySQL/Redis → Tomcat(9080) → DS 后端(12345) → DS 前端(5180) → 基座(2024) → 按需 7081/7083。
注意：子应用（7081/7083/5180）首次编译要 1–3 分钟，期间进入对应页面会白屏/转圈，**刷新即可，不是故障**。

### 2.1 DS 后端启动命令（standalone，本地联调用）

```bash
cd <dolphinscheduler 仓库根目录>
CP="dolphinscheduler-standalone-server/target/standalone-server/conf"
for d in dolphinscheduler-standalone-server/target/standalone-server/libs/*/; do CP="$CP;${d}*"; done
<JDK8>/bin/java -server -Xms1g -Xmx2g -cp "$CP" org.apache.dolphinscheduler.StandaloneServer
```

健康检查：`curl http://127.0.0.1:12345/dolphinscheduler/login/auth-mode` 应返回
`{"type":"PORTAL","projectCreationEnabled":false}`。

### 2.2 DS 前端启动命令

```bash
cd dolphinscheduler-ui
node node_modules/vite/bin/vite.js --port 5180 --strictPort --host 127.0.0.1
```

基座侧配套改动（已做）：`dlite-front-main/static/main/config_dev.json` 中 dolphinscheduler
子应用 `entry` 指向 `http://localhost:5180`。**端口变更必须同步改这里**，否则子应用挂载错乱。

### 2.3 DS 集群模式（Master/Worker）部署说明

测试/生产环境不用 standalone，而是集群模式。本集成的改造**全部在 `dolphinscheduler-api` 模块**
（身份源/项目封禁/shim 涉及的接口层），Master/Worker 不暴露 HTTP 接口、不加载 security 配置，
因此**改造代码只影响 ApiApplicationServer 一个角色**。

**与 standalone 的差异总览**：

| 项 | standalone（本地联调） | 集群模式（测试/生产） |
|---|---|---|
| 进程 | 单进程，内嵌 ZK | ApiApplicationServer + MasterServer + WorkerServer（AlertServer 可选）+ **外部 ZooKeeper** |
| 改造代码落点 | standalone-server 一个包 | 只需部署到 **api-server**；master/worker 用同一份构建产物即可（相关类不在其执行路径） |
| 元数据库 | 本机 MySQL | 三个角色**必须同一个** dolphinscheduler 库，否则项目/流程数据互相看不见 |
| 注册中心 | 内嵌 ZK TestingServer | 外部 ZK（各角色 `application.yaml` 的 registry 段） |
| HTTP 端口 | 12345 | api-server 默认为 **12345**（master/worker 无 HTTP 端口） |
| UI | vite dev（5180） | **仍由 nginx 托管** `/dolphinscheduler/ui/`（§1 的 nginx 配置不变）；api-server 自带的 ui 不需要 |

**构建**（与 §5.1 同一个前置：bom 里 mysql 驱动 scope 已改 compile）：

```bash
./mvnw clean install -Prelease -DskipTests -Dspotless.check.skip=true -Dmdep.analyze.skip=true -Djacoco.skip=true
# 产物：dolphinscheduler-dist/target/apache-dolphinscheduler-3.2.2-bin.tar.gz
```

**配置**（解包后，各角色目录下 `conf/application.yaml`）。三份预配置模板已备好（`海豚子插件/` 目录，
`api-server / master-server / worker-server-application.集群部署.yaml`，需按环境修改处均有 `[CUSTOMIZE]` 注释）：

- **api-server**（唯一需要安全改造配置的角色，§3.1 整段都配在这里）：
  `spring.profiles.active=mysql` + 数据源 + `security.authentication.type=PORTAL` +
  `portal.validate-url`（内网门户）+ `trusted.shared-secret` + `project-creation.enabled=false`。
- **master-server / worker-server**：只配 `mysql` profile 数据源 + registry（外部 ZK 地址）。
  **不需要** security/portal 段（配了也不加载）。
- **worker-server** 额外注意 `dolphinscheduler_env.sh`（JAVA_HOME 等）——worker 是真正执行
  任务的进程，环境变量按测试机实际情况配。
- **alert-server**：可选，不接告警可不起。

**启动顺序**：ZooKeeper → MySQL → `bin/dolphinscheduler-daemon.sh start api-server` →
`start master-server` → `start worker-server`。
（`bin/install.sh` 仅首次初始化元数据库时用；库已初始化过不要重复跑。）

**对接侧联动改动**（相对 standalone 只换地址）：

| 配置 | 集群下的值 |
|---|---|
| nginx `upstream dlite-ds` | api-server 主机：12345（多个 api-server 就列多个，ip_hash 已在模板里） |
| dlite-base `ds.sync.endpoint` | `http://<api-server>:12345/dolphinscheduler` |
| DS `portal.validate-url` | 内网门户，如 `http://10.200.8.134:18888/dlite-portal/oauth/token/getUser` |

**集群模式排障补充**：

- 项目/流程在某个页面看不到 → 先确认三个角色连的是**同一个**元数据库；
- 工作流能保存但提交/运行卡住 → 查 master 日志；worker 未注册时界面报 "query worker group fail"
  （standalone 内嵌无 worker 时也会报，属正常；**集群必须真起 worker** 才能跑任务）；
- api-server 返回 401 且日志有 portal 校验异常 → validate-url 网络不通或密钥不一致（§5.2 / §3.1）。

## 3. 开关类配置总表（重点）

> 这些配置不打开/不一致时，现象都是"看着像坏了"，**先查这张表**。

### 3.1 DS 侧（`dolphinscheduler-standalone-server`）

| 配置 | 位置 | 当前值 | 作用 / 不开的后果 |
|---|---|---|---|
| `spring.profiles.active` | `src/main/resources/application.yaml` | `mysql` | **改 mysql 必须配合 §5.1 的驱动 scope 改造**，否则 package 后无法启动 |
| `security.authentication.type` | 同上 | `PORTAL` | 身份源开关。PASSWORD=原生登录；PORTAL=基座统一鉴权 |
| `security.authentication.portal.validate-url` | 同上 + **打包产物 conf** | `http://127.0.0.1:9080/dlite-portal/oauth/token/getUser` | 门户校验地址。**源码与 target 产物是两份**，package 会覆盖产物（见 §5.2） |
| `security.authentication.portal.cookie-name` | 同上 | `dlite_login_token` | 门户会话 cookie 名 |
| `security.authentication.trusted.shared-secret` | 同上 | `ds-dev-trusted-secret` | 服务通道共享密钥，**必须与 dlite-base 的 ds.sync.shared-secret 一致** |
| `security.project-creation.enabled` | 同上 | `false` | **项目写操作封禁**（P1）。false=仅服务通道可建/改/删项目，浏览器直连返回 30001（USER_NO_OPERATION_PERM 当前用户没有操作权限）；true=放开（仅应急） |
| `security.authentication.portal.admin-users` | 同上 | 空 | **附加通道**（可选）：逗号分隔白名单，名单内影子用户强制为 DS ADMIN（用于服务通道 X-Portal-User 等无门户类型信息的场景）。浏览器路径的默认规则是**门户用户类型动态映射**（见下行），一般不配 |
| （无配置项）validate-url 返回的门户用户 `type` | 门户用户类型，运行时返回 | — | **角色动态映射（默认机制，2026-11-25 起）**：门户 type 0=超级管理员/1=管理员 → 影子用户自动 DS ADMIN；其余 → GENERAL。**双向同步**（门户降权/提权，DS 跟随），仅作用于密码为 NULL 的影子用户，内置 admin 等本地账号不受影响 |
| `ds.sync.*`（dlite-base 侧） | 见 3.2 | — | 基座→DS 项目同步总开关，**默认全关** |

### 3.2 dlite-base 侧（项目同步开关，**默认全部关闭**）

部署位置（本地）：`apache-tomcat/webapps/dlite-base/WEB-INF/classes/application.properties`。
生产应走部署配置注入，**不要只改本地产物**（重部署即丢）。

| 配置 | 作用 | 说明 |
|---|---|---|
| `ds.sync.enabled` | 同步总开关 | **false 时基座建项目完全不会同步到 DS**（也不产生任何登记数据），本次"建了项目海豚看不到"就是这个原因 |
| `ds.sync.endpoint` | DS API 前缀 | 含 `/dolphinscheduler`，如 `http://127.0.0.1:12345/dolphinscheduler` |
| `ds.sync.shared-secret` | 共享密钥 | 必须等于 DS 的 `trusted.shared-secret` |
| `ds.sync.housekeeper-user` | 管家账号 | 门户用户名，用于成员授权/撤销；建议用 DS admin（本地为 `admin`） |
| `ds.sync.backfill-enabled` | 存量回填 | 启动时把无映射的存量基座项目补同步（一次性用途，验证完可关） |
| `ds.sync.retry-delay-ms` | 重试周期 | 默认 300000（5 分钟），失败自动幂等重试 |

同步行为：基座建项目 → 同事务登记 `dlite_project.t_project_sync_rel`(PENDING) → 提交后
经服务通道在 DS 建项目（创建人=门户用户）→ 成功置 SYNCED；失败置 FAILED 由定时任务重试。
可在 `t_project_sync_rel` 查 `sync_status / fail_reason` 排查。

### 3.3 基座前端侧

| 配置 | 位置 | 说明 |
|---|---|---|
| qiankun 子应用注册表 | `dlite-front-main/static/main/config_dev.json` | `apps[].entry`；dolphinscheduler 指向 DS UI 端口（现 5180）。**端口变了必须改** |
| dev 代理 | `dlite-front-main/config/webpack.dev.config.js` | `/dolphinscheduler → http://127.0.0.1:12345`；`/dlite-*` 三条 → `http://127.0.0.1:9080`（**是 9080 不是 8080**，8080 被本机 ZK 管理台占用，见 §5.3） |

### 3.4 菜单/权限数据（dlite_auth 库）

| 项 | 说明 |
|---|---|
| 菜单表 | `dlite_auth.t_function_dict`（`multiMenu` 体系的唯一权限源） |
| `auth_flag` | **0=需要权限控制（要走角色授权），1=不需要权限控制（所有人可见）**。要"菜单权限控制"必须是 0 |
| `all_parent_code` | 顶层菜单=`/`，二级=`/<父code>/`（**必须带斜杠**，否则 view/children 查不出子菜单——DML 易错点） |
| 角色授权表 | `dlite_auth.t_function_type_rel`（owner_type：1=用户，2=角色，owner_id 对应） |
| 授权入口 | 安全中心→角色管理（7081）；菜单树管理：菜单管理（7083，/sys/menu） |

## 4. 标准操作 SOP

### 4.1 首次部署 checklist

1. MySQL 导入：`dolphinscheduler-dao/src/main/resources/sql/dolphinscheduler_mysql.sql`（67 表 + admin）。
2. DS 打包前：**bom 的 mysql-connector scope 改 compile**（见 §5.1），再 `package -pl dolphinscheduler-standalone-server -am`。
3. 配 DS `application.yaml`：mysql profile 数据源、`type: PORTAL`、validate-url、shared-secret。
4. dlite-base 配 `ds.sync.*`（§3.2），需要存量项目时开 backfill。
5. 菜单 DML 录入数据开发菜单（检查 `auth_flag`、`all_parent_code` 两个易错字段，§3.4）。
6. 启动全链路（§2），逐项健康检查（§2.1 + 门户登录 + 数据开发首页出统计图）。

### 4.2 验证"基座建项目 → 海豚可见"

1. 基座空间配置建项目；2. `select * from dlite_project.t_project_sync_rel;` 应有 PENDING→SYNCED；
3. `select name,user_id from dolphinscheduler.t_ds_project;` 应有该项目（owner=创建人影子用户）；
4. 海豚项目管理页可见（创建人=普通用户也可见，DS 可见性=被授权项目 ∪ 自己创建的项目）。

### 4.3 验证菜单权限控制

1. 建普通用户+角色（安全中心），不授权 → 调 `POST /dlite-portal/multiMenu/view/top?systemCode=dlite-dolphinscheduler` 应无数据开发；
2. 角色管理里给角色授权数据开发菜单 → 再调应出现；superadmin/管理员任何时候都可见。
3. 注意：基座 UI 已改为**完全尊重后端 multiMenu 结果**（`dolphinschedulerMenuShim.js` 不再强制补菜单）。

### 4.4 会话调试技巧（免登录调接口）

门户登录有验证码，接口调试可直接造会话：Redis 写
`SETEX global:<任意token> 1800 '<PortalUser JSON>'`，请求带 `Cookie: dlite_login_token=<token>`。
PortalUser JSON 字段从真实会话复制（`docker exec redis redis-cli keys 'global:*'` 可查）。

## 5. 排障速查（按现象）

| # | 现象 | 根因 | 处理 |
|---|---|---|---|
| 5.1 | package 后启动报 `Cannot load driver class: com.mysql.cj.jdbc.Driver` | 上游 bom 把 mysql-connector 管理成 `test` scope，驱动不进 assembly | `dolphinscheduler-bom/pom.xml` 该依赖 scope 改 `compile` 重新打包 |
| 5.2 | 数据开发进入后跳回门户页 | DS `portal.validate-url` 指向远程/错误地址，cookie 校验失败 401 | 改**打包产物** `target/standalone-server/conf/application.yaml`；注意重打包会用源码值覆盖 |
| 5.3 | 基座主题/接口 404、405 | dev 代理指向 8080，但 8080 是本机 ZK 管理台 | 代理 target 用 **9080** |
| 5.4 | 子应用页面混合（安全中心壳+菜单管理内容）、点了没反应 | 集成期在 `loadApp` 加的地址守卫拦截了跨应用跳转（**已删除**）；若回归检查 `index.jsx` 的 loadApp 是否又被加上 | 保持 loadApp 为上游逻辑 |
| 5.5 | 调 DS/门户接口返回 XML 而不是 JSON | **内容协商陷阱**：不显式带 `Accept: application/json` 时按 `*/*` 返回 XML | 所有 DS/门户 HTTP 客户端必须显式声明 Accept（ds-base 的 DsProjectClient 已修，两处同款坑） |
| 5.6 | `npm start` 报 `--openssl-legacy-provider is not allowed` | dlite 前端要用 **Node 17**（fnm 有 v17.9.1）；Node16 不认该参数 | `export PATH=/d/workspaces/develop/fnm-windows/data/node-versions/v17.9.1/installation:$PATH` |
| 5.7 | DS `start.sh` 报 `Invalid initial heap size: -Xms4g` | 本机内存不足以按默认 4g 起堆 | 用 §2.1 命令（1g/2g）直接起 |
| 5.8 | 数据开发子应用混入 lvmai-mdm 内容 | 5173/5174/5175 被 MDM 前端 vite 占用（裸 `vite` 命令会解析到 DS UI 的 node_modules 二进制但 cwd 是 MDM） | DS UI 固定用 5180（§2.2），并同步 config_dev.json entry |
| 5.9 | 子应用页一直转圈 | 九成是后端/子应用 dev server 没起或还在首编译 | 按 §2 清单查端口；子应用首编译 1–3 分钟，刷新即可 |
| 5.10 | 安全中心/菜单管理 404 空白 | 对应子应用（7081/7083）没起 | 各自目录 `npm start`（Node17） |
| 5.11 | "更多"里两个数据开发 | legacy dlite-studio 旧菜单（code=105）未下线 | 前端 shim 已全局过滤；根治：`t_function_dict` 把 105 那棵置 `del=1` |
| 5.12 | 项目同步 FAILED，reason 含 `Unexpected character ('<'` | 即 §5.5，ds.sync 客户端收到 XML | 已在 DsProjectClient 修复，重部署 dlite-base |
| 5.13 | 定时任务/session 类异常 `token 失效` | 门户会话 TTL 30 分钟 | 重新登录；调试用 §4.4 |
| 5.14 | 宿主机改了 nginx 配置、reload 了，容器内还是旧值 | **单文件 bind mount + vim**：vim 保存是新 inode，容器仍持旧文件 | `docker restart <容器>`；以后编辑用 `vim -c 'set backupcopy=yes'` 或 `cat new > old` 原地写；改完用 `docker exec <容器> grep ... <conf>` 确认容器视角 |
| 5.15 | 集群部署替换了 jar/重启后 conf 配置还是旧值 | `api-server/conf/application.yaml` 是 **`bin/install.sh` 安装时生成的副本**，与 jar 无关、重启不刷新 | 直接改各角色 `conf/application.yaml`（进程真正读的就是它）；**勿重跑 install.sh**（会做库初始化/升级） |
| 5.16 | 数据开发页跳海豚原生登录页（DolphinScheduler 用户名密码框），时好时坏，与是否过期无关 | **qiankun 启动竞态**：`bindQiankun` 订阅全局状态时基座状态已存在会立即回调触发 trusted 交换，早于 `getAuthMode()` 置位 portalMode → 交换失败（测试 nginx 不注 X-Trusted-Client 头，10043）→ finally 无 sessionId 强制跳 /login（2026-11-25 测试环境实证） | 已修复：auth-mode 探测提前到订阅全局状态之前 + trusted 交换/兜底跳转到 portalMode 双保险。修复后真实过期时由 service.ts 统一 `window.location.href='/portal'` 回基座 |
| 5.17 | 测试库执行建表脚本报 `Unknown collation: 'utf8mb4_0900_ai_ci'` | 该 collation 是 MySQL 8.0 专属，5.7 不支持 | collation 改 `utf8mb4_general_ci`（5.7/8.x 通吃） |
