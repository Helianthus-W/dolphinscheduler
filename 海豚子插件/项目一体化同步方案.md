## 2. 总体架构

### 2.0 身份源开关（决策 1 落地，核心变更）

**ON：废弃 DS 自有认证过滤，统一走基座认证。** 落点极轻：DS 的 `LoginHandlerInterceptor`（`LoginHandlerInterceptor.java:64-96`）本就把身份解析委托给 `Authenticator` SPI（`authenticator.getAuthUser(request)`），新增 `PortalAuthenticator` 并以 `security.authentication.type: PORTAL` 选择即完成切换，401 行为沿用拦截器既有逻辑。两条身份来源：

| 路径 | 机制 | 场景 |
|---|---|---|
| **浏览器** | DS 透传请求中的门户会话 cookie（`UserConstants.COOKIE_NAME`，实证 `AccessUtil.java:73`）→ 调门户校验接口（优先复用 `POST /dlite-portal/oauth/token/getUser` 转发 Cookie；如实测偏重则门户新增轻量 `/auth/validate` 只回用户名）→ 返回门户用户名；**短 TTL 本地缓存**（默认 30s，可配）防每请求都打门户 | qiankun 子应用与基座同源，cookie 自然随请求到达 DS |
| **服务** | 请求头 `X-Portal-User: <用户名>` + `X-Trusted-Client: <共享密钥>`（常量时间比对，复用现有 trusted 密钥机制）；密钥合法即信任断言用户名 | dlite-base 同步服务、未来网关/其他后端到 DS 的调用 |

两路汇合到同一身份解析：**门户用户名 → 查 DS 用户，无则登记影子用户行（GENERAL_USER，复用现有建号逻辑；密码置随机不可用值，保证 OFF 档影子账号也无法登录 DS）→ 写入 `Constants.SESSION_USER`**，后续授权校验零改动。

> **关于「影子用户」**：DS 的数据模型以 user_id 关联一切（`t_ds_project.user_id` 创建人归属、`t_ds_relation_project_user(user_id,perm)` 授权、工作流/审计操作人、`SESSION_USER`），不可能去除用户行——那等于重构 DS 核心表。ON 档下 DS 用户表只是**技术引用表**：唯一携带真实语义的是 userName（=门户用户名，权威在门户），密码/会话不存在于 DS，邮箱/时区等为占位默认值（可选二期加档案同步钩子，门户可改名/禁用时经 `updateUser`/`user.state` 同步）。即：**认证与用户信息权威始终只有门户一份**，DS 影子行是接入统一身份的必要登记（与现网 TRUSTED 自动建号同一机制，6.5 验收实证）。

**ON 档的结构性收益**：
- **DS 会话体系整体旁路**：不签 sessionId，`SessionService` 7200s 硬过期与滑动续期问题（`qiankun子应用接入方案.md` 6.4-4 遗留）**不复存在**；登出 = 基座登出，门户会话失效 → 校验失败 → 401；
- DS 登录端点（`/login`、`/login/trusted`）不再被前端调用（保留兼容一段时间，后续清理）；DS 登录页仅在 OFF 档出现；
- 前端简化：移除 `useTrustedLogin` 换取流程与 `sessionId` 请求头（`service.ts` 401 三态/迟到快照逻辑随之退役，仅保留「401 → 跳基座登录」）；子应用启动时由基座全局状态/接口告知 authMode 决定装配哪条链路。

**OFF：DS 原生认证完整保留**（PASSWORD/LDAP/TRUSTED 换取及全部既有前端逻辑），开关回切即回退，适合灰度与应急。

## 3. P1：创建同步 + DS 项目级只读

### 3.1 创建同步（dlite-base）

- 挂点：`ProjectServiceImpl.save` 新增分支（`id == null` 时）通过 `TransactionSynchronizationManager.registerSynchronization` **afterCommit** 触发同步；不拉长基座事务。
- `ProjectDsSyncService.syncCreate(project, creatorUserName)`：
  1. 直连 DS 调创建（`X-Portal-User: creatorUserName` + `X-Trusted-Client` 断言身份，无会话概念；身份源=ON 的必要配套，见 §2.0）；
  2. 预查重名：`queryProjectListPaging` 或按名查（避免 `PROJECT_ALREADY_EXISTS` 落入重试死循环）；
  3. `POST /projects`（projectName=cnName，description）；
  4. 写映射表 `t_project_sync_rel(base_project_code, ds_project_code, SYNCED)`；
  5. 任何失败写 `FAILED + fail_reason + retry_count`，`@Scheduled`（建议 5 分钟）扫描重试；重试先做存在性核对（按 ds_code 查 / 按名查）保证幂等。
- 幂等原则：所有同步操作先查后写；重试安全。

### 3.2 映射表（dlite-base 库）

```sql
CREATE TABLE t_project_sync_rel (
  id                BIGINT PRIMARY KEY AUTO_INCREMENT,
  base_project_code VARCHAR(64)  NOT NULL,
  ds_project_code   BIGINT       NULL,
  sync_status       VARCHAR(16)  NOT NULL DEFAULT 'PENDING',  -- PENDING/SYNCED/FAILED/DESYNCED
  fail_reason       VARCHAR(512) NULL,
  retry_count       INT          NOT NULL DEFAULT 0,
  create_time       DATETIME     NOT NULL,
  update_time       DATETIME     NOT NULL,
  UNIQUE KEY uk_base_code (base_project_code)
);
```

### 3.3 DS 项目级只读化

- **后端封禁（核心）**：新增配置 `security.project-creation.enabled: false`（默认 true 兼容现状）；`ProjectsResourcePermissionCheck.permissionCheck` 读取该配置，false 时拒绝返回 `USER_NO_OPERATION_PERM`。
- **同步通道豁免**：封禁只拦「人类用户直连创建」。同步服务调用自带 `X-Trusted-Client` 头——在 DS 侧加一个简单的请求级标记（Filter 校验 trusted 头合法后写入 ThreadLocal，`createProject` 检查时优先放行），即服务端到服务端调用不受封禁影响（创建人身份仍为真实用户）。
- **前端配套**：`views/projects/list/index.tsx` 隐藏「创建项目」按钮及行内 编辑/删除/工作流组 操作列（项目级操作）；项目设置（`/projects/:code/preferences`）只读。项目内工作流/任务开发全部保留。**注：工作流组（worker group）按钮归属项目级还是集群级，实施时核对后定**。
- 只读化后 DS 项目来源唯一 = 基座同步，映射表天然完备（孤儿项目见 §6 存量处置）。

## 4. P2：切换同步（自动跟随跳转）

- **基座 payload 补码**：`project/queryPage` 及 projectChange 用到的项目查询 SQL 联 `t_project_sync_rel` 带出 `dsProjectCode`；`dlite-front-main` 的 `projectChange` 透传整个 project 对象（实证 `:786-793`），payload 自动带上，**基座前端零改动或近零改动**。
- **DS 消费**（dolphinscheduler-ui 新增，复用 `useQiankunState` 全局状态回调）：
  1. 收到 `project` 键且含 `dsProjectCode` → 存入 `useCurrentProjectStore`（pinia）；
  2. **跟随跳转**：project 变化事件触发时，若当前路由匹配 `/projects/:projectCode/*` 且 code ≠ 新值 → `router.replace('/projects/{newDsCode}')`（无映射则停留在原页并提示「当前项目未同步到调度侧」）；
  3. **挂载进入**：进入数据开发模块落在项目列表时，高亮当前项目卡片并提供「进入当前项目」快捷入口（不劫持首页统计页）；
  4. 项目列表按 `dsProjectCode` 匹配高亮。
- DS 各项目内页已在 URL 上带 projectCode，跟随跳转仅一次 `replace`，无状态残留问题。

## 5. P3：全生命周期同步

### 5.1 改名同步
- 挂点：`ProjectServiceImpl.save` 的 `id != null` 分支 afterCommit → `PUT /projects/{dsCode}`（name=cnName, description）。
- 调用身份：创建人会话优先；创建人已无权/不存在时回退到 **DS 管理会话**（见 5.3 管家账号）。

### 5.2 删除同步（约束反向纳入基座）
- **基座 `POST /project/delete` 改为先校验后删除**：
  1. 查映射；无映射 → 直接删（无 DS 侧影响）。
  2. 有映射 → 以管家/owner 会话调 DS 查询该项目**工作流定义列表**（`process-definition` 查询接口）：
     - 存在定义 → **拒绝删除**，返回业务错误「该项目在数据开发模块存在工作流，请先在数据开发中清理后再删除」（约束反向纳入，实证依据 `deleteProject:478-485`）；
     - 无定义 → `DELETE /projects/{dsCode}`，成功则继续基座删除；DS 调用失败（网络/超时）→ **拒绝删除**（删除是破坏操作，fail-safe 宁可阻断）。
  3. 全部成功才走原有基座逻辑删。

### 5.3 成员授权同步
- 三个写入点挂 afterCommit（`ProjectServiceImpl.save:83` 创建写创建人除外——创建人即 owner 无需授权）：
  - `addProjectUserRel` 手工绑定（`ProjectController.java:181`）→ `POST /users/grant-project-by-code` 逐个授权（perm=7）；
  - 权限审批通过（`ProjectAuthApproveServiceImpl.java:80-82`）→ 同上；
  - 成员解绑/移除 → `POST /users/revoke-project`（仅 admin，用管家会话）。
- **管家账号**：授权/撤销/删除兜底需要一个 DS 管理身份（项目 owner 是各创建人本人，不能要求他们配合）。方案：预置一个门户/DS 管理员账号（如现有 `admin` 或新建 `dlite-housekeeper`），dlite-base 配置其用户名，同步服务以 `X-Portal-User: <管家用户名>` + 密钥头执行管家操作——与创建同步同一断言通道，不引入新凭证类型。**管家身份只用于授权类与删除兜底，项目创建永远归真实创建人**（对应决策 1）。

### 5.4 用户映射
- 统一用户名约定：DS 用户名 = 基座登录名（trusted 自动建号已实现该约定）。成员同步时按用户名查 DS 用户（`/users` 分页查询或新增 by-name 查询），不存在则先 trusted 换取触发建号。

## 6. 存量处置（上线脚本）

1. **基座存量项目回填**：扫 `t_project_info_data del=0` 无映射记录者，按「创建人（t_project_user_rel 中创建记录或 create_user 字段）身份」在 DS 建项目 + 创建人授权 + 写映射；冲突（DS 同名）→ 人工清单。
2. **DS 孤儿项目**：只读化后 DS 中凡不在映射表的项目均为历史孤儿；提供只读清单报表，由业务决定归档/重建映射，脚本不自动删除。
3. 回填与重试均走同一 `ProjectDsSyncService`，保证幂等。

## 9. 风险与对策

| 风险 | 对策 |
|---|---|
| DS 同名项目导致创建反复失败 | 同步前按名预查；重试先核对存在性；失败单有人工处理出口 |
| 基座删除被 DS 工作流约束长期卡住 | 错误信息明确指引「到数据开发清理」；业务上可推「项目归档」流程（del=1 已支持）替代物理清理 |
| 创建人离职/改名导致会话换取失败 | 创建同步用创建人身份换取失败时 fail-fast 记录 FAILED（不静默降级为管家创建，保证归属语义），重试 + 人工 |
| 生产网络 dlite-base→DS | 直连白名单 + 密钥环境变量；超时与熔断参数化 |
| 门户不可用（PORTAL 档） | DS 过滤器 fail-closed：校验超时/失败返回 401（浏览器跳基座重新登录）；服务通道（密钥头）不依赖门户、不受影响 |
| 缓存与登出即时性 | 身份缓存 TTL 默认 30s：基座登出后 DS 侧最迟 30s 内失效，可接受；如需更强一致性可调低 TTL |
| 断言头伪造 | DS 只信任「密钥合法」的 `X-Portal-User`（常量时间比对）；浏览器路径只认 cookie→门户校验，绝不直接采信无密钥的用户头；生产收敛 DS 仅内网可达 |
| token 头路径（`LoginHandlerInterceptor` :68-79 的 API token） | **已决策：PORTAL 档保留**——下一阶段定时调度改造将直接调用 DS API，token 凭证路径继续可用；废弃范围仅是会话/登录路径，两条路径在代码中本就分离、互不影响 |
| 切换跳转打扰用户 | 仅 project 变化事件触发时跳转；列表页不强制跳；无映射不跳 |

## 10. 验收清单

1. 基座新建项目（普通租户账号）→ DS 项目列表出现同名项目，创建人一致，创建人可在 DS 内建工作流。
2. DS 项目管理页无任何创建/编辑/删除入口；直接 `POST /projects`（无 trusted 头）被 10093 拒绝；带 trusted 头的服务调用成功。
3. 基座项目改名 → DS 项目名跟随。
4. 基座删除有工作流的项目 → 拒绝并提示；清空工作流后删除成功，DS 侧项目消失。
5. 基座项目加成员 → 该成员 DS 可见项目；移除成员 → DS 不可见。
6. 基座顶栏切换项目 → DS 处于项目内页时自动跳转到新项目总览；项目列表高亮当前项目。
7. 同步服务宕机/超时 → 基座创建不受影响（映射 FAILED），恢复后定时重试成功。
8. 存量回填脚本 dry-run 输出清单，执行后两端项目一一对应。
